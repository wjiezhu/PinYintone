# 新版需求 vs 当前代码 —— 差距核对

针对《Pinyintone 新版开发需求》逐条核对 `main`（`a01957c`）的实际状态。
**需求文档明确「以下为开发需求，不能视为功能已实现」，本文只陈述现状差距，不代表任何功能已完成。**

## 一、阻断性冲突（必须先决策，否则其他工作会白做）

### 1. 三阶段流程与「不设统一实验任务」直接矛盾

- **需求**：用户自主选择练习内容、时间和次数，不设置统一实验训练任务。
- **现状**：`ToneSequencer` 强制 `pretest → training → posttest`，前测走完自动进训练，
  训练词集练遍才解锁后测；`pretest` / `posttest` 为裸测（不显示任何评价性反馈）。
- **牵连**：CLAUDE.md 的禁令 6、训练/测试词集不重叠、`assessmentSetVersion`、
  `TrainingPhase.showsFeedback`、`PhaseViews`，以及 `phase` 字段的全部语义。
- **决策点**：三阶段是整体删除，还是降级为「用户可选的自测模式」？
  两种做法对数据字段和 CLAUDE.md 的改动范围完全不同。

### 2. 新旧数据分开保存

- **需求**：新版数据与旧版数据分开保存，不直接合并统计；旧数据归档，不删除或覆盖。
- **现状**：所有记录同表，靠 `schemaVersion`（现为 5）区分。这是「可分层」而非「分开保存」。
- **决策点**：新建独立表/库，还是保留同表但强制按版本分区导出？

### 3. 上线范围没有列出送气练习与教师看板

- **需求**上线范围：声调练习、TTS 示范、录音、回听、静态颜色、基频曲线、自由文本、
  文字建议、学习记录、积分。
- **现状**：另有**送气检测（关卡 1）**、**教师看板 + 班级码**两大模块在线。
- **决策点**：这两块是保留、下线，还是不进入研究数据？需求文档未提及。

## 四、与需求相抵触的现有实现

### 1. 无依据的音节级诊断

- **需求**：本次反馈只能使用实际分析支持的信息；只有整词距离时，不生成音节级错误诊断；
  不声称用户发生了某种偏误。
- **现状**：`ToneTrainingViewModel.directionHint(for:)` 在一声分支**不做任何测量**，
  只要该音节没通过就直接返回 `.shouldStayHigh`（「要一直保持高，别往下掉」）。
  这是在无证据的情况下断言偏误类型。
- 其余声调（2/3/4）确有 `segmentScores` 音节级 DTW 支撑，属于「有依据」。

### 2. TTS 参考音未经教师核对，且已知有问题

- **需求**：TTS 参考音及声调标注需由教师核对，包含三声变调、轻声等语境处理。
- **现状**：`SpeechService` 用 `AVSpeechSynthesizer` **实时合成**并算法整形
  （去下倾 + 重平滑 + 向理想轮廓混合），无教师核对环节。
- 代码中**没有三声变调（sandhi）逻辑**；轻声仅作为 `tones` 里的 `5` 标签存在。
- 且 `docs/LEVEL_TONE_SCORING.md` 已记录：该参考音的一声轮廓自身带下倾，
  是此前评分方向反转的成因之一。

### 3. 自由文本的词条提示

- **需求**：自由文本不能默认具有教师核对过的词条提示。
- **现状**：关卡 3 用 `pinyinConverter.toneSequence(for:)` 自动推声调并生成理想参照，
  未标记「未经核对」。

### 4. 关卡 3 缺平调词走向闸门（既有缺陷，非新需求引入）

关卡 3 与关卡 2 共用打分管线且同样显示等级，但没有走向闸门，
同一发音在两个关卡会得到不同判定。详见 `docs/LEVEL_TONE_SCORING.md`。
